# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Repository status

This directory is currently **design/planning stage only** — it contains no source code, build tooling, or tests yet. `docs/IMPLEMENTATION_PLAN_v2.md` is the concrete build plan; `docs/archive/` holds the original design drafts (`BACKGROUND.md`, `MULTI-AGENT-GUIDE.md`, `PROMPT.md`, `PROJECT-SETUP.md`) for historical/rationale value only — they describe an earlier, superseded SMB-mount transport (see "Architecture decision" below) and should never be implemented literally. There is no `agent_core.py`, no `config/`, `agents/`, or `locks/` directory, and no test suite to run. When asked to "implement" or "set this up," treat `docs/IMPLEMENTATION_PLAN_v2.md` as the task spec.

## Architecture decision (2026-07-23): MCP server, not a mounted SMB share

**Resolved — see `docs/PROBLEM_STATEMENT.md` and `docs/SOLUTION_RECOMMENDATION.md` for full context.** The original design (`docs/archive/BACKGROUND.md`, `docs/archive/MULTI-AGENT-GUIDE.md`, `docs/archive/PROMPT.md`) had every machine mount `/Users/Shared/AgentMesh` over SMB. That's superseded: running a small always-on local service is acceptable, so the coordinator now runs as a persistent MCP server process on the Mac mini, reached by Claude Code and Codex on other machines as a registered MCP server over the Mac mini's Tailscale IP/MagicDNS name — no mounting, no client-side filesystem access to the mesh root at all. Ollama-backed tooling, which doesn't speak MCP, gets a thin HTTP wrapper around the same underlying functions.

**No machine other than the Mac mini ever touches `/Users/Shared/AgentMesh` directly.** This removes the entire "does `os.replace`/rename behave atomically over SMB2/3 across mixed macOS/Linux/Windows clients" question the design was previously resting on unverified — the coordinator now only ever runs against local POSIX disk, where that guarantee is solid. It also means `smb_provision.py` and any SMB-share-provisioning scope are **dropped, not deferred**: there's no share for any client to mount, so nothing needs provisioning.

Almost everything else about the design — the mailbox/lock/atomic-write/claim-recovery logic below — carries forward unchanged. It was always good local-filesystem hygiene, not solely an SMB defense.

## Repo vs. live share split

Two distinct zones, never conflated:

- **This git repo** — source of truth for logic: the `src/agent_mesh_core/` package (see `docs/IMPLEMENTATION_PLAN_v2.md`), templates (`config/*.template.json`), `deploy.sh`, and the docs in `docs/`. Fully version-controlled; a bad change to lock mechanics is one `git revert` away.
- **`/Users/Shared/AgentMesh`** — the live data share, now local disk on the Mac mini only. Populated *from* this repo via `deploy.sh`, never edited directly and never git-tracked (see `.gitignore`). It holds runtime state only: `agents/*/inbox/`, `agents/*/state.json`, `locks/`, and the deployed `config/local_rules.json`. Other machines never touch it directly — they go through the MCP server (or HTTP wrapper) that runs on the Mac mini.

Why the split: it keeps Claude Code/Codex context windows clean (no wading through megabytes of agent heartbeats or old inbox messages) and makes logic bugs revertible without destroying live agent state.

`deploy.sh` should not reimplement Python logic in bash — e.g. the "don't clobber an existing `local_rules.json`" check belongs in `rules_template.write_local_rules_template`'s `force` flag (already unit-tested), not as a bash `[ -f ... ]` guard. **`deploy.sh` has exactly one job and it is local-only**: run on the Mac mini, which already has the package installed (`git pull` + `uv sync`) and the mesh root as a local path, and invoke `agent-mesh-bootstrap` to populate the live share's *data*. It never distributes code and never runs remotely — no other machine runs `deploy.sh` at all now, since none of them touch the mesh root.

`bootstrap_mesh`/`agent-mesh-bootstrap` (what `deploy.sh` calls) is **operator/admin tooling, not part of the runtime API** any agent process should call. It's the one thing allowed to write `local_rules.json`, and it's meant to be invoked deliberately against a specific mesh root — not wired into any agent's normal request/response loop, and not exposed as an MCP tool.

## What this system is for

`/Users/Shared/AgentMesh` is a coordination directory living on local disk on an always-on Mac mini. Multiple agents (Claude Code, Codex, and local Ollama instances) running on different machines (Mac mini host, MBP M3 Pro, and eventually Linux/Windows boxes) coordinate tasks, share settings, and exchange messages by calling the Mac mini's MCP server (or, for Ollama tooling, its HTTP wrapper) over Tailscale — never by mounting or writing to the directory themselves.

## Planned architecture

Design principle: **no single shared mutable file.** Even with only the Mac mini's local process touching disk, the design keeps an isolated inbox/outbox mailbox topology plus directory-based locking, because the underlying problem (multiple concurrent callers, no coordination) doesn't go away just because the transport is now local — it just stops needing to defend against cross-platform SMB locking specifically:

```
AgentMesh/
├── config/
│   ├── local_rules.json      # read-only rules/config for all agents
│   └── file_trees.json       # aggregated file-tree structures of the cluster (not built in v1 — see docs/IMPLEMENTATION_PLAN_v2.md)
├── agents/
│   ├── agent_mac_mini/
│   │   ├── inbox/            # other agents drop messages here
│   │   └── state.json        # heartbeat, active tasks, metadata
│   ├── agent_mbp/
│   │   ├── inbox/
│   │   └── state.json
│   └── agent_ollama_local/
│       ├── inbox/
│       └── state.json
└── locks/                    # directory-based mutual exclusion (mkdir-as-lock)
```

Key invariants any implementation here must preserve:

- **One inbox per agent, not a shared queue.** Each agent only ever writes into *another* agent's `inbox/`, never into a shared global file, to avoid concurrent-write collisions.
- **Atomic writes only.** Never write JSON directly to its destination path. Write to a temp file in the same directory with a collision-resistant name (`tempfile.mkstemp`, not PID-based), then `os.replace`/rename over the target — atomic on local POSIX disk, which is all this ever touches now that the MCP server is the only writer.
- **Locking is directory-creation based**, not file-based: `os.mkdir()` on a path under `locks/` is atomic, so lock acquisition = successful `mkdir`, release = `rmdir`. Never implement locks with a plain lock *file* (`open(...,'x')`). **No stale-lock breaking in v1** — mtime-based staleness heuristics are still avoided (not just because of SMB clock skew, which no longer applies, but because they can incorrectly break a valid long-running lock) and would need an ownership-token protocol to be safe; that's deferred, not silently built. `acquire_lock` writes a random token into `<lock_dir>/owner.token` and returns it inside a `LockHandle`; if that write itself raises, `acquire_lock` rolls back its own `mkdir` and treats the attempt as failed (self-cleanup, not a distributed-recovery mechanism). `release_lock(handle)`: missing token file or mismatched token → no-op, lock left alone; matching token → remove the token then `rmdir` the lock dir; if `rmdir` then fails because unexpected extra files are present, that **raises** rather than deleting the unknown contents or leaving a permanently-undeletable lock dir. A true hard crash between `mkdir` and a successful token write (as opposed to an in-process exception) is an accepted v1 limitation — the lock dir persists with no valid token, and clearing it is manual operator cleanup, not automatic. Releasing an already-released handle a second time is a deliberate no-op (convenience for `try/finally` cleanup), not proof the caller still held the lock.
- **Agent IDs, lock names, target agent IDs, and claim IDs are all validated** before they become path components: agent/lock/target IDs against a strict human-facing portable pattern (no separators/`..`/absolute paths), **lowercase-only** (avoids collisions on case-insensitive mounts — macOS default, Windows), and rejection of Windows-reserved device names (`CON`, `PRN`, `AUX`, `NUL`, `COM1`–`COM9`, `LPT1`–`LPT9`); claim IDs (never human-authored, always caller-supplied back from a prior claim) against their own narrower generated-format check (`validate_claim_id`) before `acknowledge_claims` or `recover_processing(claim_ids=...)` touch any path.
- **`atomic_write_json` is confined to the mesh root** — it rejects (raises) any `target_file_path` that isn't under `self.mesh_root`, and separately rejects any symlink anywhere in the path between the mesh root and the target (not just relying on `Path.resolve()` — a symlink is rejected even if it happens to resolve back inside the mesh root, for one simple no-symlinks-anywhere rule).
- **Inbox messages are claimed, then separately acknowledged — not claimed-and-deleted in one call.** `claim_inbox_messages` does the atomic `mkdir(.processing/<claim_id>/)` (retried with a new ID on a rare claim-ID collision) followed by renaming the message into it (the rename — not the `mkdir` — is what enforces exclusivity) and an atomically-written `.claim.json` sidecar (including a `claim_token`, `secrets.token_hex(16)`), and returns the claimed messages/IDs/tokens **without deleting anything**. `max_messages` (validated `1..MAX_CLAIM_BATCH_SIZE=50`) bounds *attempted* claims per call, not just successful returns — this matters because a sidecar-write failure removes a message from the inbox without returning it, and bounding only successes would let repeated failures move an unbounded number of messages into orphaned claims in one call. `acknowledge_claims(agent_id, [{claim_id, claim_token}, ...])` is the separate call that actually deletes — requiring the matching token (an integrity check against a buggy caller acking the wrong claim, not a security boundary) and reporting, per item, one of acknowledged / not-found / token-mismatch / **unacknowledgeable** (the claim dir is one of the three orphan shapes with no valid token to compare against — left completely untouched, not force-deleted). `scan_and_clear_inbox` composes both calls in one step for local, in-process callers only. This split (not the older single-call scan-and-delete) is what makes a dropped MCP connection between claim and processing safe: the un-acknowledged claim just sits in `.processing/<claim_id>/` like any other orphan. Malformed messages are quarantined (renamed aside), never left in place for a re-scan to rediscover forever; other ignored files (stray `.tmp_*`/hidden) are reported, not silently dropped. A crashed/killed claimant (or an MCP client that never acknowledges) leaves its claim in `.processing/<claim_id>/` in one of four identifiable states (empty dir, message-without-sidecar, message-with-malformed-sidecar, or a complete claim) — recoverable only via an explicit, operator-invoked `recover_processing(older_than_seconds | claim_ids, action)` call (or its `agent-mesh-recover-processing` CLI wrapper), never automatically. Critically, an *empty* claim dir is **not** a special case removed unconditionally — it's also the normal transient state of a live scanner mid-claim, so it goes through the exact same age/selection rules as every other shape (age proxied by the claim dir's own mtime); recovery should be run while the target agent is stopped. The age threshold is a heuristic, not a correctness guarantee, given cross-machine clock skew — `claim_ids` is the clock-skew-proof override. `requeue`/`quarantine` fail closed (raise) on a destination filename collision rather than overwriting, and afterward clean up the sidecar and now-empty claim dir (reporting, not raising past, a cleanup failure once the message itself is already safely moved).
- **Message ordering is best-effort filename order only — no cross-machine causal or wall-clock guarantee.** Clocks skew and drift across machines; don't build logic that assumes strict delivery order without an explicit per-sender sequence number (not built in v1, since nothing currently needs it).
- **The stored message envelope is versioned and bounded**: `{schema_version, id, created_at, sender, target_agent_id, type, body}`. `body` must be a JSON object; `type` must be a non-empty, ≤64-char portable token (`[a-z0-9._-]+`); the serialized envelope has a documented max size (256 KiB, measured as compact-JSON UTF-8 bytes — `ensure_ascii=False`, no trailing newline — the exact bytes written to disk, not an approximation). `send_message` rejects anything else before writing.
- **Filesystem watchers are a v2 concern, not v1.** v1 ships polling-only (`scan_and_clear_inbox`); prefer watchers (e.g. Python's `watchdog`) over tighter polling loops once there's an actual latency need.
- **`config/local_rules.json` is read-only for agents to write, but readable via `read_local_rules`** — it's written only by the human operator (via `bootstrap_mesh`/`deploy.sh`), never by any agent process at runtime, but remote agents (who have no filesystem access once they're MCP/HTTP-only) can read it back through `read_local_rules`, exposed as an MCP tool. The same single-writer, anyone-can-read rule applies to `file_trees.json` whenever it's eventually built.

## Coordinator API shape (`src/agent_mesh_core/`, per `docs/IMPLEMENTATION_PLAN_v2.md`)

The archived `PROMPT.md` names a deployed `/Users/Shared/AgentMesh/agent_core.py` — that's superseded (see "Repo vs. live share split" above): the real package is `src/agent_mesh_core/`, an `AgentMeshCoordinator` class in `coordinator.py`, instantiated per-agent with `(mesh_root_path, agent_id)`, and running only inside the Mac mini's MCP server process. Expected surface:

- `validate_name(name)` (`names.py`) — rejects anything unsafe as a path component (separators, `..`, uppercase, Windows-reserved names); called by every method below before touching a name-derived path.
- `acquire_lock(lock_name, timeout, retry_interval) -> LockHandle | None` / `release_lock(handle)` — directory-based mutual exclusion under `locks/`, with a token written into `<lock_dir>/owner.token` and checked on release; self-cleans on an in-process token-write failure. No stale-lock breaking, no lease/timeout logic in v1. **Exposed as an MCP tool.**
- `atomic_write_json(target_file_path, data)` — confined under `self.mesh_root` with no symlinks anywhere in the path; `mkstemp` → write → flush → `fsync` → close → `os.replace` → best-effort parent-dir fsync, for any JSON in the mesh. Internal primitive, not exposed directly as an MCP tool.
- `update_state(status, tasks, extra_metadata)` — writes this agent's own `agents/<agent_id>/state.json`. **Exposed as an MCP tool.**
- `send_message(target_agent_id, message_type, payload)` — atomically drops a versioned JSON envelope (`schema_version`, `id`, `created_at`, `sender`, `target_agent_id`, `type`, `body`) into another agent's `inbox/`; requires the target inbox to actually be a directory (fails closed on a file or symlink there). **Exposed as an MCP tool.**
- `claim_inbox_messages(agent_id, max_messages=50)` / `acknowledge_claims(agent_id, [{claim_id, claim_token}, ...])` (`inbox.py`) — claim-then-acknowledge, not claim-then-delete-in-one-call: see the "Key invariants" bullet above for the full mechanics (claim token, per-item ack result, sidecar-write-failure handling). `scan_and_clear_inbox` is a local-only convenience wrapper composing both calls in one step. **`claim_inbox_messages` and `acknowledge_claims` are exposed as MCP tools; `scan_and_clear_inbox` is not** (it's for in-process/local callers only).
- `read_local_rules(mesh_root)` (`rules_template.py`) — read counterpart to the bootstrap-only writer; raises `FileNotFoundError` before the mesh is bootstrapped. **Exposed as an MCP tool** — the read side remote agents need since they have no filesystem access to `config/local_rules.json` themselves.
- `health_check()` (`mcp_server.py`) — read-only status: `{status, mesh_root, agents: [{agent_id, processing_claims: [{claim_id, shape, age_seconds}]}], locks: [{lock_name, shape, age_seconds}]}`. Locks are a top-level field, not nested under agents — `locks/` has no owning-agent metadata, so nesting them would mean inventing ownership data or duplicating every lock under every agent, both wrong. Never includes message bodies, claim tokens, or lock owner tokens. How an operator discovers stale locks/claims without SSHing in. **Exposed as an MCP tool** (and the HTTP wrapper).
- `recover_processing(mesh_root, agent_id, older_than_seconds=None, claim_ids=None, action=None)` (`inbox.py`) — operator-invoked only, never automatic, meant to be run while the target agent is stopped; reports, requeues, or quarantines claims left behind by a crashed/killed claimant across all four orphan shapes uniformly, selected by age heuristic or by explicit `claim_ids`; fails closed on a requeue/quarantine destination collision. **Not exposed as an MCP tool** — admin-only, run directly on the Mac mini.
- `bootstrap_mesh` (`bootstrap.py`) — operator/admin tooling: wires coordinator init + `local_rules.json` templating for a set of agent IDs (rejecting duplicate IDs after lowercase normalization); what `deploy.sh` actually calls. **Not exposed as an MCP tool.**

**Caller identity over MCP is an explicit `agent_id` parameter, not derived from session/transport** — there is no anti-spoofing layer, deliberately: every caller is Jacob's own tooling on his own tailnet, and the MCP server binding to the Mac mini's Tailscale interface *is* the stated trust boundary. See `docs/IMPLEMENTATION_PLAN_v2.md`'s "MCP/HTTP API design" section for the full reasoning and for what would need to change if that trust model ever does (shared tailnet, third-party tooling).

The `mcp_server.py` module that wraps the tool-flagged methods above as MCP tools is planned but not yet built — the API surface (tool list, schemas, identity model, lock-handle serialization, ack semantics) is fully decided in `docs/IMPLEMENTATION_PLAN_v2.md`'s "MCP/HTTP API design" and "Operational readiness" sections; only the framework/dispatch plumbing remains.

## Network/transport notes

- The Mac mini runs the coordinator's MCP server, bound to its **Tailscale** IP (`100.x.y.z`) or MagicDNS name — this is what avoids router port-forwarding.
- Claude Code and Codex on other machines (MBP M3 Pro, future Linux/Windows boxes) reach it by registering it as an MCP server, the same way they'd register any other MCP server — no mounting, no filesystem access to the mesh root.
- Ollama-backed local tooling, which doesn't speak MCP, reaches the same underlying functions through a thin HTTP wrapper (also bound to the Mac mini's Tailscale interface) — cheaper than teaching every non-MCP tool to speak MCP or mount a share.
- **No SMB share exists or is mounted by any machine.** The SMB-mount instructions in the archived `BACKGROUND.md` (`mount_smbfs`, `cifs-utils`/`_netdev`, `net use`) and the `smb_provision.py` module are dropped from scope entirely, not just deferred — there's no share for any client to mount, so nothing needs provisioning.
